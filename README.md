## 二、核心命题

这个项目可以直接把 LLaMA-Factory 的"训练主干"重新抽象成更干净的 Factory。核心问题：

> 给定 Model + Dataset + Budget，选择什么 Finetuning Strategy，最终得到什么 Model Artifact？

## 五、统一 Training IR

建议定义统一的 TrainingSpec：

```
TrainingSpec
├── model
├── dataset
├── template
├── objective
│   └── SFT
├── finetuning
│   ├── full
│   ├── freeze
│   ├── LoRA
│   └── QLoRA
├── optimizer
├── scheduler
├── precision
├── distributed
├── checkpoint
└── evaluation
```

**这样核心不是"调用 `transformers.train()`"，而是：**

```
训练策略 → IR → Runtime
```

SFT / LoRA / QLoRA 不再是三套并列的代码分支，而是同一个 IR 上 `finetuning` 字段的三种取值。Config Builder 负责把 IR 展开成运行时配置，Train Engine 只认 IR。

### 「单调用路径」是一条**可执行**的约束，不是一句设计口号

四种策略在 IR 上是四个取值，那么下游四个模块里就**不允许**出现按策略分叉的代码。
这条约束由 `compare.check_single_call_path` 每次运行都扫一遍，判据是：

> `model.py` / `train.py` / `eval.py` / `data.py` 这四个文件里，**一个 `kind ==` 都不许有**。

它扫的是 **token** 而不是文本行（见附录 C 的坑 96 —— 逐文本扫描会把
`compare.py` 自己文档里那句「本文件里搜不到 `if kind ==`」当成一处违规）。

## 六、阶段性落地计划

- **M0｜Spec 与 IR**：定义 TrainingSpec schema 与 Config Builder，跑通"写 Spec → 训练一次 SFT"（非自动）。
- **M1｜策略统一**：实现 full / freeze / LoRA / QLoRA 四种策略在同一 IR 下的展开与训练。
- **M2｜评测与对比**：接入 Checkpoint → Eval → Base vs Fine-tuned 对比，形成可复现的收益归因。
- **M3｜搜索与发布**：把 lr / rank / target modules 等参数化做搜索，输出 FineTune Artifact 与对比报告。

四条都落地了。M3 的「搜索」在这个项目里是**策展网格 + Pareto 前沿**，
而不是自动搜参 —— 理由见附录 B.3：这个项目的规模下，自动搜参的每一条轨迹
都比不上「把四策略 × 两个目标 × 三个 rank/挂载点铺开，然后看谁没被压制」。

## 七、验收标准

能端到端完成「FineTuneFactory」，并在其「核心」（LoRA / QLoRA / SFT 统一流水线）上给出可复现的量化结果：

- 同一份 TrainingSpec 通过切换 `finetuning` 字段即可产出 SFT / LoRA / QLoRA 三种 Artifact
- 给出 Base vs Fine-tuned 的量化对比（含显存与训练成本）

两条都满足，逐条核对见 **B.3**。

# 附录 A｜骨架、快速开始、CLI 契约、产物

## A.1 目录

```
L3-finetunefactory/
├── configs/default.json        所有口径与门槛（代码里不硬编码任何阈值）
├── data/
│   ├── models/models.json      模型注册表：只有**结构事实**，权重不在文件里
│   └── datasets/index.json     能力索引：upper / shift / reverse / sort
├── src/finetunefactory/
│   ├── rng.py                  确定性随机（sha256 派生种子）+ 指纹工具
│   ├── ir.py                   统一 Training IR：TrainingSpec / FinetuneStrategy
│   ├── schema.py               运行期对象：RunRecord / EvalResult / Artifact / PipelineResult
│   ├── config.py               配置加载 + 校验 + 扇出网格展开 + 两类摘要
│   ├── data.py                 数据集构造 + 平凡基准（chance / heuristic / majority）
│   ├── model.py                基座结构 + 确定性初始化 + 权重合并
│   ├── autograd.py             微型自动微分引擎（张量 / 算子 / MacCounter / 量化）
│   ├── plan.py                 参数计划：哪些参数可训练、显存花在哪、解析算子表
│   ├── train.py                训练循环（AdamW / cosine / warmup / 梯度裁剪）
│   ├── eval.py                 评测（全能力 + 目标能力快速探针）
│   ├── compare.py              八项核对 + Pareto + 四条期望的裁决
│   ├── lineage.py              血缘 DAG（唯一一个「吃很多、吐一个」的 pareto 节点）
│   ├── pipeline.py             编排 + 落盘 + 分级只读重建
│   ├── report.py               markdown 报告（七节，顺序即论点顺序）
│   └── cli.py                  7 个子命令（6 只读 + 1 写）
├── tests/                      空 —— 见 A.5（本项目的验证不在这里）
├── main.py                     入口（零安装：把 src/ 塞进 sys.path）
└── out/                        产物（见 A.4）
```

**形状：扇出-收拢（Fan-out then merge）。** 扇出的是 **64 份 TrainingSpec**，
收拢点是 `pareto` 这**一个**节点。它收的是前沿候选的产物，出的是一条可以被引用、
也可以被反驳的前沿。

**四层对象链**（本项目的全部内容就是这一条链）：

```
   配置 + 模型注册表 + 数据集索引
            │  扇出（sweep_cells）
            ▼
     TrainingSpec ×64          「同一份 Spec → 同一个 Artifact」
            │  plan.build_plan
            ▼
       ParamPlan                「哪些参数可训练、显存花在哪、解析算子表」
            │  train / eval
            ▼
   RunRecord + EvalResult + Artifact
            │  收拢（pareto_frontier）
            ▼
    前沿 + 裁决 + 血缘 DAG
```

**两个基准点，各回答一个问题**（这是本项目最容易被做错的一处，见 B.2）：

| 基准 | 来源 | 回答 |
| --- | --- | --- |
| `base_accs` | 微调前那个模型在四项能力上的**实测**准确率 | `gain = acc − base` —— 训练有没有帮上忙 |
| `chance_accs` | `1 / 输出字母表大小`（四项都是 0.125） | `interference = mean(chance − acc)` —— 训练有没有把不相干的能力踹到乱猜以下 |

## A.2 快速开始

```bash
# 1. 先看任务本身：不需要任何产物
python main.py list --out out                # 64 个规格一眼看完

# 2. 跑完整条流水线（本机约 12 分钟，写 134 个文件）
python main.py run                           # → out/

# 3. 看结论（只读，从产物重建，不会重跑）
python main.py compare                       # 基准点 + 对比矩阵 + 显存分解
python main.py frontier                      # Pareto 前沿 + 各轴冠军 + 常数轴告警
python main.py explain shift/full/sft_response_only   # 单份 Spec 的全貌
python main.py artifact shift/lora/r8/qv/sft # 产物摊开：张量表 / 合并 / 量化
python main.py dag --dot --frontier-only     # 只画收拢那一半

# 4. 报告
#    out/report.md 由 run 一并写出（34 KB，七节）
```

## A.3 CLI 契约

7 个子命令：**1 个写 + 6 个只读**。

| 命令 | 写? | 它回答的问题 |
| --- | --- | --- |
| `run` | ✅ 唯一写命令 | 跑完整条流水线并落盘 |
| `compare` | 只读 | 基准点是什么、64 格各自涨了多少、显存花在哪 |
| `frontier` | 只读 | 哪些方案没被完全压制、每条轴谁最好 |
| `explain <spec>` | 只读 | **这一个**是怎么配的、跑成什么样、为什么在这个位置 |
| `list` | 只读 | 64 个规格的清单 |
| `artifact <spec>` | 只读 | 导出的产物到底是什么（张量表 / 合并差 / 量化误差） |
| `dag` | 只读 | 血缘图（ASCII 摘要或 Graphviz DOT） |

三条约定：

- **`--out` 只属于 `run`。** 其余子命令是只读观察者，不写任何东西 ——
  观察者会改状态是最容易把人绕晕的一类设计。
- **只读子命令不重算任何东西。** 它们从 `result.json` + `runs.jsonl` +
  `evals.jsonl` + `artifacts/*.json` 拼出对象；两个例外都是**载入**而不是重算
  （`artifact` 读产物元数据，`dag` 重建血缘图 —— 否则 `--dot` 只能打印一句提示）。
- **`explain` 同时接受 `spec_id` 和报告里的行名**（`shift/lora/r8/qv/sft`）。
  只认一种的话，读者从报告里复制回来的那一行会「查无此 spec」，
  而这个报错会让人以为报告和结果对不上。

退出码：`0` 正常；`1` 未知 spec / 未知标识；`2` 找不到产物目录、配置或参数错误。

## A.4 产物清单

`out/` 一共 **134** 个文件：

```
out/
├── result.json          407 KB  摘要：Spec / 前沿 / 裁决 / 八项核对 / 代价表
├── runs.jsonl           194 KB  每行一次训练运行（64 行）
├── evals.jsonl           66 KB  每行一次评测（64 行）
├── lineage.json         164 KB  血缘 DAG（392 节点 / 592 边，无环）
├── report.md             34 KB  报告正文（七节）
└── artifacts/
    ├── <spec_id>.bin          裸 float32 小端，无头部、无对齐
    └── <spec_id>.json         旁证元数据：张量表 / 合并核验 / 量化误差
```

**为什么 `runs.jsonl` 与 `evals.jsonl` 要分开，而不是并进 `result.json`**：
它们都是「按规格数增长」的表，而 `result.json` 是摘要。分开的另一个后果更要紧 ——
`evals.jsonl` 缺失时，报告的 `gain` / `interference` 两列会变成「未知」，
而**「未知」和「0」必须长得不一样**：`0` 是「训练毫无作用」这个看起来完全正常的结论。

**为什么产物是裸 float32、连一个魔数都没有**：`Artifact.payload_bytes` 是**算术值**
（`Σ 参数量 × 4`，由参数表推出）。只有文件里**只**放浮点数，这条等式才成立。
加一个长度前缀或一点点对齐，等式就会差出固定的几十字节 —— 而那个差看起来
完全像「正常的序列化开销」。这条等式因此成了本项目唯一一处「声明值 vs 实测值」的
强核对，每次运行核对 64 个产物，`artifact` 子命令还会把它再对一遍磁盘文件大小。

## A.5 关于 `tests/`：本项目的验证不在这里

这个工作区其它项目的骨架里有一个 pytest 套件（`L2-modelgenomefactory` 是 131 条）。
**本项目没有**，而这是一个有意的取舍，不是漏掉的：

这个项目的每一条关键不变量，都只能在**一次真实的训练 + 评测 + 导出**上验证 ——
「解析算子表是否等于计数器实测」「合并回基座的最大绝对差」「梯度解析值是否等于
数值差分」「4-bit 的量化误差是否严格大于 8-bit」。它们的输入是一份 `ParamPlan`
和一次训练之后的权重，而构造这份输入的成本正好等于跑一遍流水线。

所以验证被放进了**流水线自身**：`compare.py` 的八项核对在每次 `run` 时对
**每一个规格**跑一遍，结果进 `result.json["counters"]["checks"]`，进报告第六节，
并且是 `acceptance` 的门槛。这不是「用运行时检查代替测试」——
恰恰相反：把这八条写成 64 个 `pytest.mark.parametrize` 的用例，
效果与现在**逐字相同**，只是它们不会在别人 `run` 的时候跑。

代价要说清楚：**这八项核对只在 `run` 的时候跑**。只读子命令读的是一份已经
核对过的产物，它们**不会**在你改完代码之后替你重新核对。改 `compare.py` /
`plan.py` / `autograd.py` 之后必须重跑一次 `run`，否则报告里的 ✅ 是上一次的。

**这套核对真正抓到过东西。** 见附录 C 的坑 100 与 101：梯度引擎里有两处
静默的错误（一处梯度别名、一处 N 倍重复累加），它们让 LoRA 的梯度大了 4 倍，
而**原来的梯度核对看不见它们** —— 因为它挑元素时只取叶子列表的**头一个**，
而那个叶子恰好是 `emb`，永远不受影响。把这条核对修成真正的探测器之后，
两处错误立刻显形，而它们推翻的正是「LoRA 学不动」这个此前写在配置注释里的结论。

# 附录 B｜实测结果

## B.1 环境与实测开销

| 项 | 值 |
| --- | --- |
| Python | 3.13.12（要求 `>= 3.12`，为了 `math.sumprod`） |
| 第三方依赖 | **零** |
| 平台 | Windows 11 / 单机 |
| 模型 | `tiny`：`vocab=28, d_model=16, n_layers=2, n_heads=4, d_ff=32, max_len=64`，5,648 参数 |
| 网格 | 8 个 cell × 4 能力 × 2 目标 = **64 规格** |
| 训练口径 | 48 步 / batch 8 / seq_len 16 / lr 3e-2 / cosine + 8 步 warmup |
| 整趟 `run` | **725.7 s**（≈ 11.3 s/规格，其中基础评测 0.52 s） |
| 产物 | 134 个文件 / 2.1 MB |

时间几乎全部花在**八项核对**上，而不是训练：梯度数值差分对每个规格要做
16 个元素的中心差分，每个元素是两次前向 + 一次反向。这是刻意的取舍 ——
用 12 分钟换「64 个规格的每一份计划都被验过梯度」。

## B.2 基准点：随机初始化的基座在四项能力上**全都低于乱猜**

这是本项目所有结论的前提，所以它单独成节。

| 能力 | chance（乱猜） | 基座（微调前实测） | 基座 − chance |
| --- | --- | --- | --- |
| upper | 0.1250 | 0.0417 | **−0.0833** |
| shift | 0.1250 | 0.0521 | **−0.0729** |
| reverse | 0.1250 | 0.0312 | **−0.0938** |
| sort | 0.1250 | 0.0729 | **−0.0521** |

未训练模型的 argmax 被「哪个 token 的 unembedding 范数最大」主导，
而那个 token 与正确答案无关 —— 所以它比均匀乱猜**还差**。这不是噪声。

**这条数据的后果是实质的**：如果 `interference` 拿实测基座当基准，
那么「干扰」就恒为负数（一切都成了提升），而且**参数越多的策略提升越大** ——
于是 `full` 会算出「干扰最小」，把结论**恰好反过来**，而报告里看不出任何异常。
所以干扰必须用 chance 当基准（`interference = mean(chance − acc)`，正 = 被踹到乱猜以下），
而收益用实测基座（`gain = acc − base`，问的是「训练有没有帮上忙」）。

两个问题，两个基准。合成一个「微调质量分」会让「涨了 5 个点但掉了 12 个点」
和「只涨了 5 个点」看起来一样。

## B.3 两条验收标准

### B.3.1 ✅ ① 同一份 TrainingSpec 切换 `finetuning` 字段即可产出 SFT / LoRA / QLoRA 三种 Artifact

**成立。** 一次 `run` 产出 **64 份产物**：

| 策略 | 规格数 | 产物字节 | 可训练参数 |
| --- | --- | --- | --- |
| `full` | 8 | 22,592 B | 5,648 / 5,648 |
| `freeze` | 8 | 10,432 B | 2,608 / 5,648 |
| `lora` | 24 | 4,096 / 16,384 / 17,408 B | 1,024 / 4,096 / 4,352 |
| `qlora` | 24 | 同上 | 同上 |

「切换字段」这件事的可执行证据是**单调用路径核对**：

```
单调用路径（无 if kind ==）  ✅  扫了 4 个模块，命中 0 处
```

`model.py` / `train.py` / `eval.py` / `data.py` 里一个 `kind ==` 都没有。
四种策略的差异全部收敛在 `plan.build_plan` 里一次展开成**参数计划**，
训练与评测只认计划。

### B.3.2 ✅ ② Base vs Fine-tuned 的量化对比（含显存与训练成本）

**成立。** 报告第一节给基线，第二节给 64 行对比矩阵（gain / 干扰 / 参数 / 产物 /
显存 / FLOPs），第三节给**逐列显存分解**。

**显存这一列必须分解着看，因为它的最大一项与策略无关：**

| 策略（同能力 `reverse`） | 基座存储 | 适配器 | 梯度 + 优化器 | **激活** | 合计 |
| --- | --- | --- | --- | --- | --- |
| `full` | 22,592 B | 0 | 67,776 B | **131,072 B** | 221,440 B |
| `freeze` | 22,592 B | 0 | 31,296 B | **131,072 B** | 184,960 B |
| `lora` r8 qv | 22,592 B | 4,096 B | 12,288 B | **131,072 B** | 170,048 B |
| `lora` r32 qv | 22,592 B | 16,384 B | 49,152 B | **131,072 B** | 219,200 B |
| `lora` r8 **all7** | 22,592 B | 17,408 B | 52,224 B | **131,072 B** | **223,296 B** |
| `qlora` r8 qv **4-bit** | 4,240 B | 4,096 B | 12,288 B | **131,072 B** | 151,696 B |
| `qlora` r8 qv 8-bit | 7,064 B | 4,096 B | 12,288 B | **131,072 B** | 154,520 B |
| `qlora` r8 all7 4-bit | 4,240 B | 17,408 B | 52,224 B | **131,072 B** | 204,944 B |

激活那一项只依赖 `d_model × n_layers × seq_len × batch`，**四种策略完全相同**
（131,072 B，占 `qlora` 4-bit 总显存的 **86.4%**）。于是：

- **「QLoRA 的显存只有 full 的 1/8」是错的。** 基座那一项确实从 22,592 B 掉到
  4,240 B（**1/5.3**），但合计是 151,696 / 221,440 = **0.685**，只有 1.5 倍的差。
  这个数字在报告里逐列摊开，藏进「其它」里的话上面那句错误结论会自动成立。
- **`lora` r8 all7 的显存（223,296 B）比 `full`（221,440 B）还大 1,856 B。**
  这是「LoRA 省显存」这个说法的一个反例，而且是网格里刻意留的一格：
  全挂 7 个投影的适配器 + 它的梯度 + 它的优化器状态，正好越过全参微调。

**训练成本只有一列，而且是常数。** 见 B.5。

## B.4 八项核对：64 / 64 全通过

| 核对项 | 结果 | 实测 |
| --- | --- | --- |
| IR 序列化往返 | ✅ | 64 份 Spec 逐字段往返 |
| 单调用路径（无 `if kind ==`） | ✅ | 扫 4 个模块，命中 0 处 |
| 适配器合并回基座 | ✅ | 48 个适用（16 个 full/freeze 不适用），最大绝对差 **2.154e-14**，容差 1e-5 |
| 解析算子表 vs 计数器（**逐算子**） | ✅ | 64 个规格，`add` / `matmul` / `scale` … 逐项相等 |
| 代价三路互校 | ✅ | 64 个规格，①解析 == ②实测（单样本） |
| 梯度数值差分 | ✅ | 64 份计划，最差相对误差 **5.788e-10** |
| 量化误差单调性 | ✅ | 4-bit 是 8-bit 的 **17.3451 倍**（0.0709 / 0.0041） |
| 产物字节 = 声明值 | ✅ | 64 个产物，算术值与落盘字节逐位相等 |

三件事值得单独说：

- **合并差是 2.154e-14，不是 0。** 合并走手写三重求和、前向走 `matmul`，
  浮点累加顺序不同，逐位相同的概率是零。所以判据是 `≤ 容差` 而不是 `== 0.0`；
  反过来，**如果它真的等于 0**，那说明其中一份实现被换成了另一份（oracle 复用），
  报告会把它单独报成 `identical_suspect`。
- **「不适用」与「没通过」分得开。** `full` / `freeze` 没有适配器，合并与梯度对
  它们是 `applicable=False, ok=True`。把它们算作「通过」会让「8/8 通过」
  在只有一部分真的被验过时也成立。
- **量化误差是 17.3 倍，不是 2 倍。** 位数从 8 掉到 4（一半的信息），
  误差涨了 17 倍 —— 这就是 4-bit 的代价，也是 `qlora_trades_gain_for_memory`
  那条期望的实测依据。

## B.5 四条设计期望：**3 条被推翻，1 条成立**

这一节是本项目最值钱的输出。

| 期望 | 裁决 | 证据 | 实测 |
| --- | --- | --- | --- |
| `lora_interferes_less_than_full` | **❌ 被推翻** | 24 对 | 只有 **7/24** 个配对上 full 的干扰更大；中位差 **−0.0087**（正 = full 更差） |
| `lora_reaches_full_gain_on_target` | **❌ 被推翻** | 24 对 | 只有 **3/24** 个配对达到 `gain_lora / gain_full ≥ 0.9`；中位比 **0.451** |
| `qlora_trades_gain_for_memory` | **❌ 被推翻** | 16 对 | 只有 **7/16** 个配对「显存更低且 gain 不更高」同时成立；中位显存比 0.913，中位 gain 差 **+0.0260** |
| `response_only_beats_all_tokens` | ✅ 成立 | 28 对 | **23/28** 个配对上 `response_only` 的 gain 更高；中位差 **+0.0833** |

### 被推翻的三条，各自说了什么

**① `lora_interferes_less_than_full` 被推翻。** 中位差 −0.0087 意味着
**LoRA 的干扰反而略大于 full**，而 24 对里只有 7 对支持原期望。
这条期望背后的直觉是「改得少 → 忘得少」；实测说明在本项目的规模下，
**「改得少」并不等于「忘得少」** —— 全参微调有足够的容量在学会新能力的同时
把旧能力一起抬起来（见 `gain` 的分布），而 LoRA 的低秩约束让它对
目标能力的拟合更「偏」，代价落在别处。

**② `lora_reaches_full_gain_on_target` 被推翻，而且差得最远。**
中位比 **0.451**：LoRA 在目标能力上只拿到 full 不到一半的增益。而这条期望的
阈值 `acceptance.lora_gain_ratio = 0.9` 不是拍的 —— 它写在配置里，
读者可以自己调它做敏感性分析（调完会立刻看到裁决翻转，这正是它该有的行为）。

> ⚠️ **这个 0.451 有一个必须跟着它一起读的边界条件**：网格里全部 64 个规格
> 共用 `lr = 0.03`，而这个步长是**按 full 标定的、恰好是 LoRA 的谷底**
> （B.7 实测：LoRA 的峰值在 0.1，在 0.03 处准确率恰好等于乱猜）。
> 所以「LoRA 只拿到不到一半」里有一部分是**共享步长**造成的，不是容量上限。
> 本项目刻意没让策略各标各的 lr —— 那会让「策略」不再是网格里的唯一变量 ——
> 代价就是这条裁决带着一个已知方向的偏差。**取舍写在这里，不是漏掉的。**

> ⚠️ **这条结论曾经是反的，而反转的原因是引擎有 bug。** 在修掉附录 C 的
> 坑 100 / 101 之前，同一份网格给出的中位比是 **1.000**（「LoRA 完全达到 full」）。
> 两处梯度错误让 LoRA 的梯度大了 4 倍，于是它**看起来**学得又快又好。
> 修完之后是 0.451。**上一段落里所有 `gain` 相关的数字都是修完之后重测的。**

**③ `qlora_trades_gain_for_memory` 被推翻，但推翻的方向很有意思。**
中位显存比 **0.913** —— QLoRA 确实省显存，但只省 8.7%，因为激活那一块
（131,072 B）与策略无关，把基座量化的收益稀释掉了（见 B.3.2）。
而中位 gain 差是 **+0.0260**，即 **QLoRA 的 gain 反而略高**。
「拿 gain 换显存」这个框架在实测下不成立：它更像是「基本不损失 gain，
顺手省一点显存」—— 而这一点只有在把显存逐列摊开之后才看得出来。

### 成立的那一条

`response_only_beats_all_tokens` 成立（23/28，中位 **+0.0833**）：
只在回答的 token 上算损失，比在全序列上算损失更好。这条最符合直觉，
而且它是四条里唯一一条**在同一次修复前后都成立**的。

### 常数轴：`train_flops` 对 64 个规格取同一个值

```
⚠️ 这些轴在本次网格里是常数（每个规格都取同一个值），它们对前沿没有贡献：
    训练 FLOPs = 2,169,372,672
```

这不是 bug，是**真的**：所有格子跑同样的 48 步 × batch 8，而结构上四种策略的
单样本解析算子数也是同一个数。报告会自动把这条说出来 ——
否则读者看到「冠军表里这条轴的冠军是整个前沿」会以为表坏了。

它的含义要写清楚：**四条目标轴实际上只有三条在起作用**，而「训练成本」
在这个口径下**不是一个可优化的维度**。要让它有区分度，得让网格里的
steps / batch / seq_len 产生差异 —— 而它们刻意对全部规格统一，
那正是「策略之间可比」的前提。这是一个真实的张力，不是可以两全的东西。

**而 `train_flops` 本身是估算，不是实测**：`③ = ① × steps × 有效批 × 3 × 2`，
其中 `3` = 前向 1 + 反向 2、`2` = 每个 MAC 两个 FLOP。两个系数都是经验值，
所以报告里 ③ 和 ② **分开写**，核的是「它是不是真按这个式子算的」，
不是「这个系数对不对」。三路里 ① 解析、② 实测，只有 ③ 是估算 ——
一颗被标成实测的估算值，是这类项目里最难被发现的一种错。

## B.7 lr 标定：**旧数字是在坏引擎上测的，已全部作废**

`configs/default.json` 的 `train._comment` 原本写着：

> lr=3e-2 是按 full 标定的：实测 lr 从 3e-2 一路加到 1.0，四种策略的准确率都**单调变差**
> （full 0.604→0.531→0.104→0.052），所以 3e-2 已在最优点附近

**这段结论作废了。** 它是在梯度引擎带着附录 C 坑 100 / 101 两处静默错误时测的，
而那两处错误对四种策略的影响**不一样**（LoRA 的梯度被放大 4 倍，full 不受影响）——
所以「四种策略一起变差」这个观察本身就不成立。

修完之后重测（`upper` / `sft`，其余口径与生产一致 ⇒ **单点粒度 1/24 = 0.0417，
只能读趋势，不能读单点**）：

| lr | full | freeze | lora | qlora |
| --- | --- | --- | --- | --- |
| 0.01 | 0.2708 | 0.1042 | 0.1562 | 0.1667 |
| **0.03**（生产值） | **0.3958** | 0.2292 | **0.1250** | 0.1771 |
| 0.1 | 0.1250 | **0.3021** | **0.1979** | **0.2083** |
| 0.3 | 0.0729 | 0.1146 | 0.1458 | 0.1250 |
| **峰值在** | **0.03** | **0.1** | **0.1** | **0.1** |

终损失给出**同一个排序**（full 在 0.03 最低 1.283；freeze / lora / qlora 三个都在 0.1
最低，1.707 / 2.389 / 2.415）—— 两个信号独立地指向同一个结论，这不是抽样噪声。

### 旧结论错在哪：**四个策略没有一个单调**，峰值位置也不同

- 「四种策略都单调变差」**是错的**。只有 `full` 在 0.03 之后掉下去；
  `freeze` / `lora` / `qlora` 三个的峰值**都在 0.1**，在 0.03 处还没到顶。
- 更要紧的是：`lr = 0.03` 对 `lora` 是**四个点里最差的一个**，准确率 **0.1250** ——
  **恰好等于乱猜**（chance = 1/8 = 0.1250）。它在 0.1 能拿 0.1979。
- 所以旧注释里那句「四种策略共用同一个 lr 是公平的」**不成立**。

### 这条对 B.5 的裁决意味着什么

`lora_reaches_full_gain_on_target` 被推翻（中位比 0.451）是在一个
**对 full 最有利、对 LoRA 恰好在谷底**的步长下测的。这不是那条裁决的反例，
而是它的**边界条件**，必须写在它旁边：**那 0.451 里有一份是共享步长造成的，
不是 LoRA 本身的容量上限。** 要把它分开，得让每种策略各标各的 lr ——
而那会让网格里「策略」不再是唯一变量，所以本项目**刻意没做**，
只把这个偏差量写出来。这是取舍，不是遗漏。

> **口径边界**：上表是**一个能力（upper）、一个目标（sft）、n_eval=24** 的四个点。
> 粒度 1/24，「0.1250 恰好是乱猜」里有多少是巧合，这张表回答不了。
> 它够用来推翻「四个都单调」这种**定性**断言，不够用来给任何一个单点下结论。

## B.8 可复现性边界

**可以复现的**：同一台机器、同一份配置、同一个 Python 版本下，`run` 的产物
**逐字节相同**。种子由 `sha256` 从内容派生（不用内建 `hash()`），缓存键用内容摘要
（不用 `id()`），浮点进指纹前先量化 —— 这三条让「同一份 Spec → 同一个 Artifact」
是一句可以被验证的话，而不是一句设计口号。

**不可复现的**：`counters.timings` 里的秒数，以及 `report.md` 里由它渲染出的那一行。
它们随机器负载变化，**不进任何摘要**。

**口径变了要重跑**：`version_digest` 覆盖模型注册表 + 数据集索引 + 扇出网格，
它变了必须整体重跑；`protocol_digest` 覆盖评测口径（显存估算系数、容差、报告阈值），
它变了只需重出报告。两者分开，是因为「输入变了」和「口径变了」是两件事 ——
合成一个摘要会让报告无法回答「我改的是哪一类」。

# 附录 C｜坑（94–108）

编号接着 `L2-modelgenomefactory` 的 93。

### 94. `build_lineage` 自相矛盾：先给每个产物接上前沿，然后再拒绝它们

**症状**：`ValueError: 落选者被接进了前沿：artifact:sft-freeze-1595cf0baace`。
整个流水线跑不完 —— 而这不是第一次运行，是这份代码**第一次被执行**。

**原因**：`build_lineage` 的逐 spec 循环里无条件地
`g.add_edge(art, PARETO_NODE_ID, "candidate")`，而循环之后的不变量检查
**恰好禁止**非前沿候选接进 `pareto`。两个写在不同位置的东西互相否证，
函数从来没能跑完过 —— 所以这个矛盾在阅读时不存在，只有真跑一次才会出现。

**修法**：把前沿成员**在循环之前**算出来，让那条边变成有条件的：

```python
on_frontier = {artifact_node(s.spec_id) for s in result.frontier}
...
if art in on_frontier:
    g.add_edge(art, PARETO_NODE_ID, "candidate")
```

留下来的那条检查被改名为「不变量 2（残留守卫）」并注明它现在只防未来的回归。
**教训**：「同一个函数里前后互相否证」的代码读不出来，因为读的人会默认
后面那句是前面那段的补充，而不是它的反例。

### 95. `run_pipeline` 在 `cfg=None` 时**静默丢弃** overrides

**症状**：冒烟跑本应出 21 个规格，实际出了 **64** 个。没有报错，没有警告。

**原因**：

```python
if cfg is None:
    cfg = load_config(None, root=root)
elif overrides:            # ← 只有显式传了 cfg 才生效
    cfg = deep_merge(...)
```

`cfg=None` 是**最常用**的那一种调用（读默认配置），而它恰好落在
`if` 那一支上，overrides 被丢掉了。于是冒烟脚本拿着**生产配置**跑了一遍。
唯一的线索是打印出来的规格数对不上。

**修法**：`overrides` 在两条分支上都生效。**教训**：短跑（冒烟）与长跑（出报告）
走同一条代码路径是这个骨架的设计意图，所以「短跑的参数没生效」会同时毁掉两者 ——
而它的症状是「冒烟通过」，比「冒烟失败」危险得多。

### 96. 用文本扫描实现「不许出现 `if kind ==`」，于是扫到了自己的文档

**症状**：`single_call_path` 核对 FAIL，命中的是 `compare.py` 里
那句「本文件里搜不到 `if kind ==`」—— 它是一句**注释里的说明**。

**原因**：逐行子串扫描分不清代码和散文。

**修法**：改用 `tokenize` 扫 token，跳过 `COMMENT` / `STRING` / `FSTRING_MIDDLE`，
只在「`NAME('kind')` 紧跟着同行 `OP('==' | '!=')`」时才算命中。
另外：词法分析本身失败（`IndentationError`）时**报成一处违规**而不是跳过 ——
跳过意味着「没搜到」，而真相是「没搜」。

**教训**：一个用来抓违规的检查，它自己的文档就是最容易触发它的地方。
凡是「搜关键字」式的检查，都要先问「它会不会搜到关于自己的说明」。

### 97. `result.counters` 赋值太晚 → **前沿恒为空，而报告照常生成**

**症状**：`frontier: 0`，`n_usable: 0`，64 个点全部进 `skipped_nan`。
但报告生成得出来，每一节都在，只是「前沿」那一节永远是空的。

**原因**：`compare.objective_values` 从 `result.counters["costs"]` 里读 `vram_bytes`，
而代码的顺序是「先取点、后赋 `counters`」。取点那一刻 `result.counters` 还是空的，
每个 spec 的 vram 都是 `None` → `NaN`，而 `pareto_frontier` 遇到 NaN 是**按设计跳过**的。

**修法**：重排成「先让 result 自洽，再问它问题」——
`counters`（含 `costs`）先落，然后取点 / 算前沿 / 回填 `pareto_stats`。

**教训**：这正是本项目最警惕的失败形态：**没有异常、没有 NaN 泄漏到报告里、
每一张表都长得像样**，只是收拢那一半整个没在算。`skipped_nan` 这个计数器
就是为这一类失败准备的 —— 它不是「有 NaN 就报错」，而是「把跳过的点
明明白白地数出来」，因为**跳过是正确的，静默跳过不是**。

### 98. 代价三路互校拿**单样本**的解析值去比**整个训练跑**的实测值

**症状**：`three_way` 对**每一个** spec 都失败。

**原因**：① 是「一次单样本前向」的解析算子数，而代码取的是
`run.macs["total"]` —— 那是整个训练跑累加出来的 MAC。两者**同名**（都叫 macs）
但差着 `steps × batch` 倍。

**修法**：改成 `checks["macs"][sid]["measured_total"]`（同一次单样本前向的实测值）。

**教训**：同名不等于同量。这个 bug 还有一个更坏的变体：
如果 `steps × batch` 恰好等于 1，它会**静默通过** —— 而那时它同样什么都没验证。
所以核对要写「比的是哪一次的量」，不能只写变量名。

### 99. `plan.build()` 在计数区**外面**，于是 LoRA 的实测恰好等于 full

**症状**：`macs` 核对对 lora / qlora 失败，逐算子比对报 `add` / `matmul` / `scale`
三项不符，而 full / freeze 全过。

**原因**：LoRA 的适配器是在 `plan.build()` 里**并进**基座权重的
（`W + scale · (B @ A)`）。那三个算子是权重空间的（`matmul d·r·d`、`scale d²`、`add d²`），
正好是解析表里多出来的那几项。把它们放在计数器外面，实测就只剩一次
「权重已合并好」的普通前向 —— 于是 lora 的实测恰好等于 full。

**修法**：把 `build()` 移进 `with mac_counter()` 里面，并注明
**这里如果走错方向去改解析表，会把它改成错的**。

**教训**：这个失败看起来像「适配器的算子没被算进去」，真因却是
**「核对把一件事剪成了两半去比」**。症状指向的方向和真因相反，
是「两个量该不该在同一段里测」这类错误的一般形态。

### 100. `_acc` 复用了消费者的梯度列表 —— `y.grad is x.grad`

**症状**：梯度数值差分最差相对误差 0.186。而它在四个策略上表现不同，
在 `n_layers` 变化时呈现「所有非最后一层全错 + 最后一层的 `norm1` 错」的形状。

**原因**：`_acc` 在 `t.grad is None` 时写 `t.grad = g` —— **直接把消费者的列表
挂了上去**。于是两个张量共享同一个 list，一处的累加会改到另一处。
最小复现：

```python
y = x @ W; s = y + 0; z = s + b; z2 = z + x
# 反向后 y.grad is x.grad 为 True，而 y.grad 显示 [[2,2]]
# 它真实的梯度是 [[1,1]]，多出来的那一份是从 x 那条路上改过来的
```

**修法**：加 `_copy_grad`，按梯度形状拷一层。

**定位过程**（值得记，因为顺序就是方法）：① 确认数值梯度在四个数量级上
eps-稳定（排除差分本身有问题）；② 逐叶子比对解析值与数值值（拿到错误的**形状**）；
③ 变化 `n_layers` 拿到更精确的形状；④ 写出上面那个最小别名复现；
⑤ 逐算子梯度核对显示**每个算子单独都是对的**；⑥ 用一个合成注意力子图二分。
真正的线索是 ② 和 ④ —— **别名问题的特征是「错得没有规律」**，
而结构问题的特征是「错得有形状」。

### 101. `split_cols` 一份 `_bw` 挂在 N 个输出上 → 梯度大了 N 倍

**症状**：同 100（两个 bug 是在同一轮里一起抓出来的）。

**原因**：`split_cols` 给 N 个输出**共享同一个** `_bw` 闭包，而引擎对每个节点
调用一次 `_backward` —— 于是那份**完整的**合并梯度被 `_acc` 累加了 N 次。
`n_heads = 4`，所以每一个经过 `split_cols` 的梯度都大了 4 倍。

**修法**：每个输出拥有自己那一段，回填时只填自己那一片、其余补 0。
并加了宽度断言 `sum(sizes) != width` → 报错。

**教训**：全项目只有这一个多输出的算子（`concat_cols` 是单输出，验证过是对的），
所以这个 bug 的暴露面很窄 —— **而窄暴露面的 bug 正是最该被自动检查抓住的**。
它只能被梯度数值差分看见，而梯度数值差分当时恰好是瞎的（见 102）。

### 102. 梯度核对的两重失明：**一条永远为真的检查比没有检查更糟**

**症状**：修好 100 / 101 之前，梯度核对在 `full` 上是**通过**的。

**原因**（两处，都让核对看起来在验、实际没验）：

1. `_pick_elements` 取的是叶子列表的**头一个**元素 —— 而 `full` 的第一个叶子是 `emb`，
   它恰好不受那两个 bug 影响。于是 `full` 的检查是**空的**。
2. `n_checks` 默认只有 6，覆盖率太低，抽样跨不过受影响的叶子。

**修法**：`_pick_elements` 改成**在叶子之间轮转**取元素（第一个叶子的第 0 个、
第二个叶子的第 0 个……回头再取第 1 个），`n_checks` 从 6 提到 **16**。
现在 64 份计划的最差相对误差是 **5.788e-10**。

**教训**：这一条比 100 / 101 更值得记。**一条永远为真的检查比没有检查更糟** ——
它让人以为验过了。修好这两条之后，两处静默的梯度错误立刻显形，
而它们推翻的是这个项目此前写在配置注释里的一个「结论」（B.7）。

### 103. `to_dot(include=...)` 按**节点种类**过滤，却叫 `include`

**症状**：`dag --dot --frontier-only` 输出一张**空图**。

**原因**：`include` 的参数语义是「保留这些 `kind`」，而调用方传的是
`dag.ancestors("pareto")` —— 一组**节点 id**。一个都对不上，输出
`digraph lineage {}`。而空图**不是报错**：它是一份合法的 DOT，
`dot` 画出来是一张白纸，调用方只会以为「图太稀疏了」。

**修法**：拆成两个按名字区分的参数 —— `kinds`（按种类）与 `nodes`（按 id）。

**教训**：一个参数名读起来完全正确（「只画 pareto 的祖先」）、
而它的语义是另一个维度时，错的是**名字**，不是调用方。

### 104. `cli.artifact` 读错 `meta` 的嵌套层，于是**编造**了一个理由

**症状**：LoRA 产物的输出里写着 `合并：不适用 —— 没有适配器`。
而它明明有适配器。

**原因**：`artifacts/<spec>.json` 是 `Artifact.to_dict()`。`Artifact` 自己有一个字段
叫 `meta`，而它里面**又**装着 `payload`（张量表）与 `merge`（合并核验）。
代码写的是 `d.get("payload")`，而这个键在 `d["meta"]["payload"]` 下 ——
`.get() or {}` 给一个空字典，于是张量表整段消失、「布局 / dtype / 浮点数」
三行全变「未知」。

**而它在 `full` 的产物上看起来完全正常**，因为 `full` 本来就没有适配器可合并。
只有在一份 LoRA 产物上它才会说出那句**编的**话。

**修法**：不再手写嵌套路径，一律走 `Artifact.from_dict()` 之后**按字段**取。
`merge` 缺失时的文案改成「**不在**这份 JSON 里」而不是「没有适配器」。

**教训**：`.get(k) or {}` 会把「读错了地方」伪装成「这里本来就没有」。
而这种伪装在**恰好有一半样本不适用**的地方最持久。

### 105. 从磁盘渲染报告时，整张「配置要求 vs 实际裁决」的表消失了

**症状**：同一份结果，内存路径渲染 6 行，`load_full` 路径渲染一行「（空）」。

**原因**：裁决表要从配置里拿四条**声明**的期望，而 `result.json` 里
刻意不存整份配置（`cfg` 属于仓库，不属于一次运行）。载入路径上 `cfg` 是空的，
于是这张表整张消失。

**修法**：把 `expectations` 作为**独立字段**落盘（它是**声明**，不是推导量），
并在 `load_runtime` 里接回去。

**教训**：这张表要回答的恰恰是「有没有哪条期望被漏掉了」，
而它自己整张消失是最坏的一种表现 —— 少的那一行本来就没人会注意到。
**凡是「检查缺失」的表，它自己不能有沉默的缺失模式。**

### 106. 「正好等于乱猜」被读成「高于乱猜」

**症状**：基准表里 `sort` 的「基座 − chance」是 `0.0000`，而「读作」那一列写着「高于乱猜」。

**原因**：`"低于乱猜" if delta < 0 else "高于乱猜"` —— `0` 落在了 `else` 里。
而这个边界不是假想的：`sort` 在默认口径下**恰好**是 0.1250 vs 0.1250。

**修法**：三支分开写，「正好等于乱猜」有自己的说法。
**教训**：`0` 在「低于 / 高于」的二值判断里必须被显式安置 ——
它归到哪一边，读者就会得到哪个结论，而这两个结论的方向完全不同。

### 107. `targets` 写成模块列表 → `TypeError: unhashable type: 'list'`

**症状**：配置里把 `"targets": ["q_proj", "v_proj"]` 写成了模块列表，
报错是 `TypeError: unhashable type: 'list'`，位置在**成员测试**那一行。

**原因**：`targets` 是一个**名字**（进 `sweep.target_sets` 查），不是模块列表本身。
`x in dict` 遇到 list 直接抛 `TypeError` —— 报错发生在成员测试这一行，
读者看不到下面那句「不在 `sweep.target_sets` 里」。

**修法**：先查类型再查成员，给它一句能读懂的话：
「应当是一个**名字**（qv / qkvo / all7 之一），要按模块列表写请先在
`sweep.target_sets` 里给它起个名字」。

**教训**：一个自然的误解应该得到一条**关于那个误解**的报错。
类型错误发生在成员测试里，等于用一条与真实原因无关的异常替读者盖住了答案。

### 108. 「LoRA 学不动」是引擎 bug 的产物，而它已经被写进了配置注释

**症状**：无报错。`configs/default.json` 的 `train._comment` 里写着一整段
基于实测的 lr 标定结论：「lr 从 3e-2 一路加到 1.0，四种策略的准确率都单调变差
（full 0.604→0.531→0.104→0.052）」。同一时期还有一组「LoRA 的 rank 与挂载点」
标定数字。

**原因**：**这些都是在一台带着坑 100 / 101 的引擎上测的。**
那两处错误对四种策略的影响不一样（LoRA 的梯度被放大 4 倍，full 不受影响），
所以「四种策略一起变差」这个观察本身就是假的。
修完之后，`lora_reaches_full_gain_on_target` 的裁决从 **confirmed（中位比 1.000）**
翻成 **refuted（中位比 0.451）**。

**修法**：重测（B.7 的四点表），并把作废这件事**写进 README 和配置注释**，
而不是悄悄改掉数字。重测的结果比旧结论更有用：**四个策略没有一个单调**，
`full` 的峰在 0.03 而另外三个的峰都在 0.1 —— 于是旧注释里那句
「四种策略共用同一个 lr 是公平的」被推翻，而生产网格用的正是 0.03。

**教训**：这是本项目最值得留的一条。**「实测结论」的可信度上限，
就是当时那台引擎的可信度** —— 而一个数字一旦写进注释，它就开始看起来像事实。
判据不是「这个数字是跑出来的」，而是「它是在一台被验过的机器上跑出来的」。
所以项目里那句 `⚠️ 这条结论曾经是反的` 比正确的那组数字更值钱。
